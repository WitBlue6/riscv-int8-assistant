# 在 RISC-V RTL 中运行的微型 Transformer

这是原 INT8 指令助手旁边的独立实验。原助手先分类再返回固定回答；本实验由一个 **3,744 参数、单层、单头的因果 Transformer** 逐个预测字符，遇到 EOS 结束。没有调用外部模型 API，也没有让 Python 代替固件生成回答。

它很小，只用于学习与验证。训练集为八组短句，成功重现这些训练句子不代表能回答新问题。这里没有部署 0.5B 模型，也没有自研 RISC-V CPU。

## 这次各部分实际在哪里运行

```text
电脑 Python 训练：corpus.json → train.py → weights.h / weights.json
                                    ↓
main.c + weights.h → RISC-V 交叉编译 → Transformer 固件
                                    ↓
现有 Vsoc RTL 仿真器加载这个固件
    ↓
PicoRV32 执行：读字符、归一化、注意力、KV 缓存、生成循环
    ↓ MMIO
四路 INT8 加速器：Q/K/V 投影、注意力输出投影、前馈层、词表投影
    ↓
RISC-V 输出 JSON → server.py 转发 → 网页显示
```

本实验复用父项目的 `picorv32.v`、`soc.sv`、`int8_accel.sv` 和 `sim/main.cpp`，没有改变原助手的 RTL 或固件。CPU 支持 RV32IM；推理全程整数运算，不需要浮点单元或操作系统。

## 模型结构：从输入一个字符到预测下一个

参数：模型宽度 16，前馈层宽度 32，最大输入上下文 32 个 token，词表 37 项（34 个普通字符 + BOS + EOS + UNK）。一个普通字符就是一个 token，不使用大模型的子词分词器。

```text
字符编号 + 位置
    ↓ 查两张学习得到的表并相加
16 维向量 x
    ↓ RMS 归一化
Q/K/V 三个线性投影 ───→ 本次 K/V 存进缓存
    ↓ 当前 Q 与已有 K 计算相关分数
只关注已有字符（因果注意力）
    ↓ 查表近似 softmax，按概率对已有 V 加权求和
注意力输出投影 + 残差 x
    ↓ RMS 归一化
16→32 前馈投影 → 裁剪 ReLU → 32→16 投影 + 残差
    ↓ RMS 归一化
16→37 词表投影
    ↓ 排除 BOS 和 UNK，选择最高分
下一个字符或 EOS
```

Q/K/V 可以先理解为当前字符用于“查询”、每个历史字符用于“匹配”、每个历史字符提供的“内容”。模型训练时学习如何生成这些向量。推理时先保存历史 K/V，后续新字符复用它们，避免重复计算历史投影。

采用单头、单层、无可学习 RMS 增益、无投影偏置、学习位置嵌入、裁剪 ReLU 的简化解码器。它有因果自注意力、残差、归一化与前馈块，属于微型 Transformer；不是 Qwen/Llama 的兼容实现，不能直接加载它们的权重。

提示词前面自动加 BOS。逐个处理提示词称为 prefill；随后反复预测、将生成 token 送回模型，称为 decode。当前最多输出 12 个 token，EOS 停止；上下文到达 32 项后停止继续调用 forward。最后一个预测可以展示，但不会超出位置表再次送入模型。

## 现有加速器怎样承接这些线性层

每个 forward 有七个逻辑线性层：Q、K、V、O、up、down、head。硬件输入最多 256 项、输出最多 32 项；本模型除了 head，其余都能一次算完。

head 输出 37 个分数，因此 [main.c](main.c) 的 `linear()` 分成 **32 + 5** 两块，分别上传对应权重行、启动硬件、取回结果。这是输出维度分块，不是把 37 改成 32，也没有丢弃后五个类别。

每个输入 token 对应 8 次硬件启动、660 个核心计算周期。每个线性层的输出均以 INT32 读取，在 CPU 上进行尺度转换；使用现有硬件的原始输出模式，不使用旧分类模型的硬件 0～127 裁剪作为所有层通用规则。

新固件加入了硬件等待超时和 ERROR 检查。当前仍由 CPU 搬权重，不含 DMA、权重常驻优化或新的流水线。真正的注意力分数与加权和仍在 CPU 上计算，不能宣称全部 Transformer 运算都在加速器里完成。

## 数值格式：为什么没有浮点也能运行

训练采用 NumPy 浮点反向传播与 Adam。导出后：

- 词嵌入、位置嵌入保存为 INT16，尺度为 32。
- 线性层权重保存为 INT8，尺度为 64。
- 进入加速器的向量限制在 -127～127，尺度为 32。
- 硬件计算出 INT32 乘加结果，CPU 除以 64（向零截断），恢复尺度为 32 的数。
- RMS 归一化使用整数平方根；注意力 softmax 使用预生成指数查找表和整数归一化。
- Q/K/V 限制到 -127～127，前馈激活限制到 0～127；残差保存在 INT32 中。

整数推理定义写在 [model.py](model.py)，C 固件实现相同的舍入和裁剪规则。浮点训练和整数推理不是逐位相同的算法，需要重新检查量化后的生成表现。本实验选择检查最终整数模型，而不是假定浮点训练成功就意味着 RTL 输出正确。

位置表和词嵌入也属于模型参数。总计 3,744 个可学习参数，导出的参数数组原始占用 4,848 字节；另有 2,050 字节指数查找表、词表字符串、代码和运行时缓存。这个数不是整个 ELF 文件大小。

## 三种运行模式与计时

| 网页选项 / 固件 | 用途 |
|---|---|
| 加速器 + CPU 逐项校验 / transformer.hex | 每个硬件 INT32 输出再用 CPU 计算一次进行比较；最适合验证 |
| 加速器·性能模式 / fast.hex | 去掉重复 CPU MAC 校验，保留相同生成逻辑；用于测量 |
| 仅 RISC-V CPU / software.hex | 所有矩阵乘法由 CPU 执行，用于对照 |

`match=true` 只在在线逐项校验模式表示成功。未在线校验的模式输出 `match=null`，不能误读成当次已做逐项校验。

`total_cycles` 从 prefill 开始到生成停止，包含归一化、注意力、缓存、数据传输、矩阵乘法和必要的跟踪记录；不包含提示词 UTF-8 解析和 JSON 输出。三种模式都记录逐步分数和状态哈希；校验模式额外计算参考乘法，其总时间不适合直接拿来声称应用加速比。

已有本版本实测，`你好：` 生成 `你好！` 和 EOS：

| 项目 | 数值 |
|---|---:|
| forward 次数（含提示词） | 7 |
| 加速器启动次数 | 56 |
| 加速器核心周期 | 4,620 |
| 加速器性能模式完整推理周期 | 368,543 |
| 仅 CPU 完整推理周期 | 565,110 |
| 同口径完整推理加速比 | 约 1.53 倍 |

这是原有零等待仿真 RAM 条件下的 RISC-V 周期比较，不是相对电脑运行 NumPy 的加速比，也不是芯片最高频率/能耗结论。重新编译或修改模型后以 [verification_report.json](verification_report.json) 为准。网页的宿主毫秒数仅表示电脑运行仿真的耗时。

## 验证包括什么

[test.py](test.py) 真正启动 Vsoc，并测试三份 RISC-V 固件：

1. 比较生成 token、每一步全部词表分数与 Python 整数参考。
2. 比较每个 forward 的状态哈希和七个投影哈希；哈希用于紧凑定位，不等于无碰撞的完整状态证明。
3. 校验模式在 RISC-V 内部逐个比较加速器原始 INT32 输出和软件结果。
4. 检查每 token 的 8 次硬件任务、660 个核心周期和 149 个线性输出检查。
5. 测试词表外输入的 UNK 回退、首尾空白清理、空输入、过长提示词、非法 UTF-8，以及 EOS、上下文上限、最大生成长度三种结束路径。
6. 检查具有相同输入前缀的两次生成，其前缀状态一致，验证因果方向和 KV 缓存行为。

八条训练样本之外的其他输入用于实现一致性和边界测试，不能当作语言任务测试准确率。词表内外非训练输入用于一致性测试；另编译最多生成一个 token 的固件，确定性验证最大长度停止。

## 文件阅读顺序

先看 [corpus.json](corpus.json) 了解数据范围，再看 [main.c](main.c) 的 `main → forward → linear`。其中 `forward()` 展示 Transformer 各步骤，`linear()` 是 CPU 和 RTL 加速器的交界。

随后用 [model.py](model.py) 的 `generate()` 对照同一整数数学流程。最后阅读 [train.py](train.py) 中浮点训练、因果掩码、反向传播和参数导出。网页服务 [server.py](server.py) 仅启动仿真、转发输出，未导入 model.py 进行回答。

可以在现有实验上继续做：更严格的量化训练、更大词表、更多数据、输入维度分块、权重驻留、注意力算子硬件化。扩展前应先确认内存、溢出边界、仿真周期和语料质量。0.5B 部署仍是远超当前规模的另一阶段。

## 输入修复与生成能力的区别（2026-09-15）

不带冒号的 `早上好` 本身包含的字符都在词表内。原固件遇到额外空格、换行或英文逗号会拒绝，并将词表问题与 UTF-8 错误合并提示。现在网页清理首尾空白，固件将其他合法未知字符映射到输入专用 UNK；非法 UTF-8 仍然拒绝。

本版本实测 `天气怎么样` 生成 `上好！`，`随便说说` 生成 `会客会接着写！`。这些是模型逐步预测的结果，不是硬编码回答，但不代表它理解了问题。多个陌生字符映射到同一 UNK，会丢失区别；后续需扩大词表或使用能够覆盖任意输入的分词方案。

生成链已打通，扩充参数只是后续工作之一。通用问答还需要广泛语料的预训练、适当的指令训练和实际评估；较大模型还需要更大存储、输入维度分块、合理的量化精度与数据搬运优化。
